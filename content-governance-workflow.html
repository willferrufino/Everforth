Content governance and web publishing workflow

A practical example of how a federal web team can coordinate requests, validate requirements, review accessibility and quality, publish through a CMS, and keep content current after launch.

From request to published page

Intake

Capture the request, intended audience, user need, content owner, deadline, source material, and required approvals.

Review

Check accuracy, duplication, plain language, records considerations, links, metadata, and whether the request belongs on the public site.

Build

Create or update the page in the CMS using approved components, semantic markup, accessible patterns, and responsive layouts.

Validate

Perform content QA, accessibility checks, cross-browser review, stakeholder verification, and regression testing for related pages.

Publish & maintain

Publish after approval, confirm production output, record the review date, and schedule the next content review or retirement decision.

Cross-team responsibilities

Content owner

Confirms factual accuracy, business need, policy alignment, and review cadence.

Content manager

Shapes content for the web, applies plain language, builds in the CMS, coordinates reviews, documents issues, and validates publication.

Design / development

Supports component behavior, technical defects, templates, performance, and accessibility fixes that require code changes.

Delivery principle:

Do not treat content, accessibility, and development as separate handoffs. Use shared acceptance criteria so issues are found before launch rather than after publication.

Definition of done for a web update

  • ✓
    Requirement confirmed. The page has a known audience, user need, owner, and approval path.
  • ✓
    Content is web-ready. The most important information comes first; headings are descriptive; language is concise and understandable.
  • ✓
    Accessibility reviewed. Heading structure, links, images, forms, keyboard use, and content relationships have been checked.
  • ✓
    CMS build validated. Components, metadata, links, responsive behavior, and page relationships work in the staging environment.
  • ✓
    Stakeholders approve. Content owner and required technical or communications partners validate the final version.
  • ✓
    Production verified. The published page is checked after release and assigned a future review date.

Example issue handoff

Issue WEB-142 — heading component renders a visual H3 as a DIV

Reported by: Content management   Priority: Medium   Owner: Front-end development

User impact: The page looks correct visually, but assistive technology does not receive the same heading structure. This makes the page harder to navigate by headings.

Expected result: The component should output a semantic heading element that matches the content hierarchy. 

<!-- Current output -->
<div class="card-title">Accessibility resources</div>

<!-- Recommended output -->
<h3 class="card-title">Accessibility resources</h3>

Validation plan: Re-test the component in staging, inspect the DOM, navigate the page by headings, and regression-test other pages that use the same component before production release.
